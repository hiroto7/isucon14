# ISUCON14 ローカル計測レポート

## 計測条件

- 公式Go実装: `isucon/isucon14` commit `53f8b627e040c30ebec600457c6c97da008b84b0`
- 構築設定: `matsuu/cloud-init-isucon` commit `d30817994a296a98661bd684cdcf21c66a4df2d8`
- VM: Ubuntu 24.04 ARM64、2 vCPU、4 GiB RAM、25 GiB disk
- Goアプリ、MySQL、nginx、matcher、公式ベンチマーカーを同じVMで実行
- 公式ベンチの計測60秒、各回の前にGoとmatcherを再起動して20秒待機
- 公式検証は3回とも成功。各回のログとプロファイルは `results/` に保存

この値はローカルARM64の単一VM上での比較用であり、大会環境のスコアと直接比較しない。

SQLの他の上位digestは各回合計0.3秒未満で、総時間では `COMMIT` が最大だった。これはperformance_schemaが集計したstatement待ち時間の合計であり、実時間や採点式そのものではない。nginxの上位通信は椅子・利用者の通知と位置更新で、リクエスト全体の平均時間は各回64–75msだった。VMのCPUは各回ほぼ使い切っており、SQLのコミット待ちとCPU競合の両方を含む可能性がある。

## 改善候補1: InnoDBログ同期 (`flush-log-2`)

`innodb_flush_log_at_trx_commit=2` の公式計測は3回成功し、スコアは3,688・4,348・3,617、中央値は**3,688**（初期中央値比104%、初期中央値より約4%増）だった。計測準備中のSSHタイムアウトも1件あり、公式ベンチを開始できなかった試行として `score: null` で保存した。候補の3回の範囲は初期状態の範囲と重なるため、現時点では採用せず、初期設定と候補設定をそれぞれ追加3回ずつ測って判定する。

## 改善仮説

MySQLの現在値 `innodb_flush_log_at_trx_commit=1` は、各トランザクションのcommit時にログを同期する設定。負荷中に多数のcommit待ちが記録されたため、値を `2` にして1秒ごとの同期にまとめる候補を試す。トランザクションの原子性や通常時の読み書き整合性は維持される一方、OSクラッシュ時に直近約1秒のcommitが失われる可能性があるため、変更の採否と再起動後の検証結果を記録する。

## 再計測・グラフ再生成

```sh
local-benchmark/.venv/bin/python local-benchmark/tools/run_benchmark.py baseline --runs 3
local-benchmark/.venv/bin/python local-benchmark/tools/plot_scores.py
```

`results/*/result.json` が計測の正本。PNGとCSVは保存した結果から再生成できる。失敗した回はスコア0にせず、失敗としてグラフに表示する。
