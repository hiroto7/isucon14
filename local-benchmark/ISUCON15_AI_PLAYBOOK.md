# AIと進めるISUCON：大幅なスコア改善のための実行指針

作成日：2026-10-07。対象：2026-10-31の競技に参加する私たちと、競技中に開発を支援するAI。

会話では「ISUCON15」と呼んでいるが、2026-10-31開催の公式名称は **ISUCON2026**。公式案内の競技時間は10:00〜18:00 JST。本書の時間配分はこの8時間を前提とする。[公式開催案内](https://isucon.net/archives/59917350.html)、[公式レギュレーション](https://isucon.net/archives/59966826.html)。当日の案内・マニュアルで変更があれば、そちらを優先する。

本書はISUCON14での私たちの109試行を振り返って作った。ISUCON15の問題、得点式、API、台数、許容遅延、最適な実装方式を予言するものではない。**ISUCON14の解法や設定値ではなく、次に何を測り、何を変え、どう判断するかを引き継ぐ。**

## 0. AIが最初に読む指示

以下を競技開始時の指示として使う。後続の節には根拠・手順・テンプレートがある。

> 目的は、当日仕様を守り、追試で再現できる最高の採用状態を作ること。
>
> 1. 当日マニュアル、規約、公式更新、提供コードを読め。得点式、失敗条件、初期化、再起動、データ保持、代替方式の許可を短くまとめ、不明点は不明と書け。
> 2. 未知の今回の問題に、過去問のテーブル・方式・設定値を当てはめるな。競技後の講評・解法が存在する前提で検索するな。
> 3. 計測前に配備コード、実行中バイナリ、設定、起動状態を確認せよ。提供済みの公式ベンチ実行方法を使い、必要なく自前構築を始めるな。
> 4. 初期ベンチと負荷中のプロファイルから、得点を生む処理の流れと現在の律速を特定せよ。仮説にはログ・SQL・コードの根拠を付けよ。
> 5. 処理1回の短縮に加えて、繰り返し回数、逐次処理、データ量、通知方式、待ち行列を調べよ。局所時間だけで採用を決めるな。
> 6. 原則1仮説ずつ実装し、公式検証・総点・狙った指標を比較せよ。性能変更をまとめる必要があれば理由と範囲を記録せよ。
> 7. 各候補を機械的に3回測るな。まず1回で方向を見て、大きく伸びた採用候補と最終状態を追加検証せよ。小差の確認に時間を使い切るな。
> 8. 正常応答、順序、一貫性、永続性、初期化を維持せよ。FAILの報告点は有効スコアにせず、失敗・中止の記録も残せ。
> 9. 改善後は負荷が増える前提で接続上限、キュー、CPU、I/Oを再測定せよ。古いボトルネックの改善を続けるな。
> 10. 停滞したら「この候補が効かない」と「システムに伸びしろがない」を区別せよ。停止前に仕様上の別方式と、仕事量を大きく減らせる余地を再点検せよ。
> 11. 新規AI・モデル変更・コンテキスト引き継ぎ時は現在状態ファイルを読め。共有環境の配備・設定変更・ベンチは直列化し、実行担当を一人に固定せよ。
> 12. 最後は最高の単発スコアの候補ではなく、正常な採用コミット・設定へ戻し、初期化と再起動後の公式ベンチを通せ。

## 1. 今回の振り返りで確認できたこと

計測の正本は [results/](results/)、全試行一覧は [all-trials.csv](all-trials.csv)、詳細は [REPORT.md](REPORT.md)。全109試行には成功98件、失敗・中止11件がある。最高値更新32件には同じコードの再測定や不採用候補も含まれ、32件の独立した改善を意味しない。109回は練習全体の回数で、競技8時間の目標回数ではない。

最初の公式コードの3回は5,104・1,951・3,549点。VM再構築後の初期中央値は4,754点。最後は116,260点で再起動後の公式検証も通った。ただしVM再構築、設定変更、別日をまたいでおり、全推移を厳密な単一条件の因果実験とは扱わない。

| 教訓 | 私たちの活動で起きたこと | 次の競技に持ち込む判断 |
|---|---|---|
| L1 得点モデルを先に読む | 満足度の数値を直接の得点律速のように扱い、後から当日マニュアルで直接得点と需要増加の効果を整理し直した | 得点の直接項、需要・負荷を変える間接項、失敗条件を分ける |
| L2 大きな仕事量を減らす | 単件の周期処理を複数件化し、接続制限と組み合わせて9,127→27,661点。通知方式の変更では旧コード55,755〜64,883点に対し115,416・116,260点 | 呼び出し回数、逐次性、不要な往復を構造から減らす候補を探す |

| L4 局所速度と総点を分ける | 最後の近傍検索SQLは平均26.7→3.2msになったが、総点115,416→109,427で戻した。コミット待ちを減らしても総点が伸びない例があった | SQL時間・API時間は中間指標。採用判断は得点経路全体を見る |

| L6 実行状態を証明する | 過去候補のGoファイルがVMに残った。旧コード比較でビルド失敗後に誤ってベンチを開始した。同じ旧コードも別日には異なる点数になった | 配備先のファイル集合、バイナリ、設定、準備成功を確認し、比較対象を更新する |
| L7 停止前に別の軸を探す | 小さな候補を多数試して何度か停止した後、当日仕様に存在した代替通知方式で大きく伸びた | 細かな候補の枯渇を全体の限界と呼ばない。仕様と仕事量を再点検する |
| L8 AIの進行を状態と成果で管理する | 得点式・プロファイル・停止判断の見直しにユーザーの追加指示が必要だった。記録とコミットがあったので途中の変更・失敗を追えた | 人間は優先順位を監督し、AIは測定、実装、検証、採否、引き継ぎまで閉じる |

以下の分析はこの観測からの一般化である。別の問題での効果の保証ではない。

### L1 得点モデルを先に読む

最初に「この処理が速くなると、何が増えて点になるか」を説明する。提供資料から次の3つを別々に抜き出す。

- **直接得点**：成功件数、処理量、重み、時間窓、ペナルティなど、採点式に入るもの。
- **間接効果**：速くすると利用者・要求数・データ量・次の処理が増える仕組み。
- **正常条件**：レスポンス、順序、整合性、遅延猶予、初期化、再起動、保持すべきデータ。

未知の値をISUCON14の値で埋めない。例えば「3秒まで遅れてよい」「履歴は消してよい」「通知方式を変えてよい」は今回の仕様に根拠が必要。マニュアルを要約するだけでなく、得点に至る実際の処理列に対応付ける。

AIの最初の成果物は、概ね次の形にする。

```text
得点項：公式資料の該当箇所、重み、成立条件
得点処理列：要求 → 前処理 → 待ち行列 → 実処理 → 確定 → 得点
クライアントの進み方：逐次 / 並列 / 応答待ち / 周期駆動
需要の増え方：固定 / 適応的 / 未確認
正常条件：即時一貫性、許容遅延、順序、再試行、永続性
初期化・追試条件：対象、実行方法、再起動後の復元
仕様上の選択肢：形式、保存方式、処理方式の許可と制限
未確認事項：推測せず、確認先と次の調査を記載
```

競技中の根拠は当日資料、公式更新、提供されたコード、実測を中心にする。ベンチ実装は提供され利用が認められる範囲で読む。未提供のベンチサーバーへアクセスしない。

### L2 大きな仕事量を減らす

私たちはSQL、索引、プール、ログ、ポーリング間隔を多数試した。一部は効いたが、最後まで大きかったのは「同じ状態を大量に取りに行く仕事」だった。もっと早く、**何回行う必要があるか、何件ずつ進めるか**を調べるべきだった。

候補探索では次を順に見る。問題によって該当しない項目は飛ばす。

| 観測する形 | 検討する変更 | 先に確認する条件 |
|---|---|---|
| 高頻度の検索で大量走査・ソート | インデックス、検索条件、取得項目、クエリ形 | 実データの件数・分布、実行計画、追加書き込み費用、初期化後にも索引が残るか |
| 1要求ごとに同じ情報を繰り返し取得 | 不変情報の再利用、要求内の一括取得 | 変更箇所、無効化、認証・権限、再初期化 |
| N件に対してN回の照会・送信 | 一括取得、複数件処理、往復削減 | 順序、一対一性、処理単位の整合性、まとめる待ち時間 |
| 読み取りのたびに履歴全体を集計 | 現在値・集計値を更新時に保持 | 更新の原子性、二重更新、復元、書き込み増幅 |
| 変更がないのに頻繁に通信・照会 | 仕様が許す変更駆動の配信、再利用 | クライアント対応、接続容量、再接続、未受信データ |
| 周期ごとに1件しか進まない | 適切な複数件化・並列化・スケジューリング | ロック、接続数、下流容量、待ち行列 |
| 大きなデータを毎回返す・計算する | 仕様を保つ範囲で生成・シリアライズ・転送を削減 | 応答構造・順序・内容の互換性、転送量、実際のCPU費用 |

「インデックスを全部貼る」「キャッシュを全部入れる」を初手にしない。頻度が高い検索や長い走査を実測で選び、検索の短縮と追加更新の費用を両方確認する。

逆に、大幅改善だけを求めて索引のような小さな変更を無視しない。今の律速を外し、次の大きな処理を回せるなら優先する。**変更行数の大きさと効果の大きさは別。**

### L3 律速の移動を追う

改善後に要求数・同時実行・データ量が増える問題では、初回負荷のプロファイルはすぐ古くなる。私たちの複数件処理では、次にDB接続が上限へ達した。通知方式を変えると、次に常時接続を収容する設定が問題になった。

大幅改善候補には、実装と同時に以下の容量確認を付ける。

- 接続プールの最大値、DB全体の接続上限、ワーカー数、開くFD数。
- キュー長、投入量と処理量、最古の待機時間、タイムアウト、再試行数。
- CPU飽和、ディスク・ネットワーク、ロック待ち、外部呼び出し。
- 複数台の配置と担当。再起動順序が変わっても復元できるか。

上限は無条件に上げない。大きすぎるプールはCPU競合やDB待ちを増やす。観測した同時数と下流の処理能力に合わせる。

初回がFAILでも、機能不整合と容量不足を分ける。例えば「報告点が上がった、接続上限エラーが明確、機能不一致はない」なら、原因を限定した容量修正を試す価値がある。FAILの報告点を採用スコアにすることとは異なる。

### L4 局所速度と総点を分ける

一つのSQLが8倍速くなっても、全体が8倍速くなるわけではない。並列リクエストの時間合計やSQL累積時間は実経過時間ではない。別の処理へ費用を移す変更もある。

各候補には次の3段階の説明を要求する。

1. **狙った指標が変わったか**：照会回数、走査行数、CPU、待ち時間など。
2. **得点処理列が速く進んだか**：成功件数、完了量、キュー解消、負荷後半の進み方など。
3. **公式検証と総点が改善したか**：候補の採否と比較条件。

指標だけ改善した場合は、追加書き込み、ロック、別の待ち、需要の変化、測定差を調べる。大幅改善が目的なら、軽微な点差を証明するために多数の反復をしない。次に効く根拠がなければ戻して候補を変える。

ただし、ある候補が効かなかったという履歴は永続的な禁止ではない。私たちの一括検索は低負荷で総点を上げず、高負荷へ進んだ後に効いた。**再試行は、新しい負荷で律速になった証拠があるときに行う。**

### L5 一貫性を仕様から守る

AIはDB往復を減らすためにトランザクションを外したり、書き込みを後回しにしたりしやすい。私たちは実際にそれで、同じ応答内の状態と統計が別時点になる不一致と、反映遅れを起こした。

キャッシュ・非同期化・ロック削減を提案するときは、次をコード変更前に書く。

```text
正本はどこか：DB / ログ / その他
一緒に見える必要がある値：対象の行・統計・状態
変更を確定する点：トランザクションのコミット等
応答を返す時点で保証すること：保存 / 受付のみ / その他
変更を読む全経路：API、集計、検索、背景処理、通知
再試行時：二重計上・重複配信・順序はどう扱うか
初期化時：何を消し、何を作り直すか
プロセス・全台再起動時：何から復元するか
遅延が許される対象と上限：当日仕様の根拠
```

許容遅延はすべての処理へ一律に適用しない。非同期処理は「設定した待ち時間」ではなく、負荷中の実際の反映遅延、キュー長、最古データの年齢を測る。永続化前に成功を返す設計なら、当日の保存・再起動要件を満たす根拠が必要。

単体テストやコンパイル成功だけで十分としない。意味のある並行更新・再試行・再接続のテストを選び、最終的には公式検証を通す。公式pass=trueでも出力されたエラー・欠落・遅延を読み、候補による新しい問題を見逃さない。

### L6 実行状態を証明する

「ホストのソースを戻した」「ビルドコマンドを実行した」と「対象サーバーがその状態で動いている」は同じではない。私たちの配備は当初、対象ファイルのハッシュだけを比較し、不要になったファイルの残留を見逃した。

配備とベンチの間に、失敗したら先へ進まない境界を置く。

```text
対象コミット・差分を記録
→ 対象へ配備（削除対象を含むファイル集合を照合）
→ ビルド成功を確認
→ 新バイナリと起動プロセスの対応を確認
→ 設定・サービス起動・依存先への接続を確認
→ 公式ベンチを実行
```

いずれかが失敗したら計測しない。実装する配備スクリプトでは各段階の終了コードを検査する。シェルなら適切に失敗で終了させ、複数コマンドを成功確認なしで流さない。ファイル削除は管理対象に限定し、ユーザーのファイルまで一括削除しない。

同じ採用コードでも、私たちの10月の再計測では旧コードが64,883点と55,755点だった。過去の最高89,355点を変更前の現在値として使うべきではなかった。別日、VM再構築、再起動、配置変更、大きな設定変更の後は比較基準を更新する。

常時接続方式へ変えた後のHTTP時間は接続継続時間を表す。ポーリング時の応答時間と同じ指標として比較しない。このような**指標の意味の変更**も記録する。

### L7 停止前に別の軸を探す

私たちは何度か「次の大きな候補がない」と判断した。しかし、その後に仕様で認められた別方式を読み直し、大きく伸びた。停止判断の前に、以下を確認するべきだった。

1. 得点処理列を最初から最後まで追ったか。目立つ統計を直接得点と混同していないか。
2. 呼び出し頻度と処理量を見たか。遅い1回だけに注目していないか。
3. 仕様上の別形式・別処理方式・保存方式を確認したか。
4. 周期、逐次処理、同時数、キューの進み方を確認したか。
5. 今の高負荷でのプロファイルか。初期の測定に基づく候補を繰り返していないか。
6. 以前の不採用候補が、現在の律速に対応するようになっていないか。
7. 部分最適によって別経路の費用や待ちが増えていないか。
8. 当日仕様の範囲内で、仕事そのものを削減できる余地を一巡したか。

次の測定で区別できる仮説があれば、調査を進める。期待効果が小さい候補しかなく、説明が推測の繰り返しになり、残り時間を回収できないなら停止する。

停止理由は「これ以上絶対に伸びない」ではなく、「現在の測定・仕様・残り時間から、次に優先する根拠のある大幅改善候補がない」と記録する。残り時間は復元・追試対策・エラー解消へ回す。

### L8 AIの進行を状態と成果で管理する

AIにコード生成を依頼するだけでは、検証の抜けと場当たり的な候補が増える。人間は得点モデル、仮説の根拠、時間配分を監督する。AIは調査から採否まで一つのサイクルを終える。

**人間の確認点**は3つに絞る。

- この変更が点に効く説明は、今回の資料と計測に基づいているか。
- 正常条件を削って点を上げていないか。実行状態が確認できているか。
- 次の候補へ進む理由、戻す理由、停止する理由があるか。

細かい実装選択ごとに承認待ちにしない。先に、許可する編集・配備・検証の範囲、共有環境の担当、クラウド操作の対象を決めて渡す。範囲が曖昧な破壊操作や新しい課金は人間が判断する。

複数の人間・AIを使う場合は、読み取り調査を分担する。DB解析、アプリのCPU・通信解析、仕様と得点処理列の確認は分けられる。ただし**共有環境の配備・設定変更・ベンチは一人の担当を通して直列化**する。別ブランチで作った候補を無断で同時配置しない。統合後は公式検証と現在の律速を測り直す。

AIの進捗報告は短く、次の形にする。

```text
事実：どのログ・測定で何が分かったか
仮説：何を変えると得点処理列のどこが進むか
変更：今回扱う範囲、正常条件への影響
結果：公式成否、総点、狙った指標、エラー
判断：採用 / 仮採用 / 不採用 / 原因修正 / 停止
次：次の候補または測定。誰が共有環境を使うか
```

## 2. 競技開始から終了までの進め方

時間は目安。仕様・環境の複雑さによって調整し、当日マニュアルが定める開始・終了・追試条件を優先する。

| 時間帯（JST） | 目的 | AIに要求する成果物 |
|---|---|---|
| 10:00〜10:45 | 初期状態を起動して測る。同時に当日資料を読む | 得点モデル、未確認事項、配備・復元手順、初回公式ログ、負荷中の基本指標 |
| 10:45〜12:00 | 現在の大きな律速を外す | 根拠付き候補を少数に絞り、公式検証を通る改善サイクルを回す |
| 12:00〜15:30 | 仕事量・処理構造の大きな候補を試す | 高負荷の再診断、構造変更の整合性説明、容量確認、変更前後の得点比較 |
| 15:30〜17:00 | 採用状態を統合し、追試で再現させる | 不採用候補の復元、全台の設定確認、初期化と再起動後の公式計測 |
| 17:00〜18:00 | 最終状態を固定し、壊さず完了する | 正常な採用状態・設定・復元方法・最後の公式結果・全試行記録 |

17時まで待って初めて再起動テストをするのは遅い。大きな採用変更の後にも短い復元確認を入れ、終盤は本番の台数・構成・追試条件で通す。最終確認に必要な時間より余裕が少なくなったら新しい大規模変更を止める。

### 最初の45分でやること

1. 当日資料をAIに渡し、L1の得点モデルを出させる。別の担当は環境を確認する。
2. 言語・実行プロセス・DB・フロントサーバー・設定・初期化経路・台数を確認する。GoやMySQLであると決めつけない。
3. 提供されたベンチ実行コマンド・バイナリ・ポータルを確認し、初期状態でまず1回実行する。
4. 同じ負荷区間でHTTP集計、DB指標、CPU・メモリ・I/O、キューを採る。起動や初期化だけのプロファイルと混ぜない。
5. 採用状態へ戻せるコミットと設定を記録する。環境対応を性能改善と分ける。
6. 仮説カードを上位3件だけ作り、最初の1件を選ぶ。ここで完全なコード理解や全ツール導入を待たない。

### 通常の改善サイクル

```text
現在の正常な採用状態・比較値を確認
→ 負荷中の測定から仮説を選ぶ
→ 候補と正常条件を記録
→ 独立した変更として実装・コミット
→ 配備成功と実行状態を確認
→ 公式ベンチ1回＋同じ負荷中の診断
→ 総点・対象指標・エラーで判断
→ 採用候補は追加検証、不採用はコードと設定を復元
→ 採用した場合は律速が移動したか測り直す
```

複数変更を一つにするのは、検証可能な一つの機能に不可分な場合に限る。例えば処理方式と必要な容量設定を組み合わせる場合は、その事実を記録する。別々に効果を断定したければ、時間のある範囲で比較を分ける。

## 3. 測定は「全部採る」ではなく「次を区別する」ために行う

以下はツールの候補であり、問題の実装言語・DB・配備条件に合うものを選ぶ。新しいツールの導入自体が目的にならないようにする。

| 調べたいこと | 最小限の測定 | 判断の注意 |
|---|---|---|
| どの要求に時間を使うか | HTTPログの件数、平均、p95/p99、エラー、上流時間、転送量。alp等でルートを集約 | 動的IDをまとめる。頻度と遅延を両方見る。接続継続時間と処理時間を区別する |
| どのDB処理が多い・遅いか | slow query log、digestの回数・累積時間・走査行数、ロック・接続状態、対象SQLの実行計画 | 閾値以下の高頻度SQLも見る。EXPLAIN ANALYZE等の実行負荷・更新の副作用に注意し、対象と実行場所を選ぶ |
| CPUを何に使うか | 実装に合うサンプリングプロファイラ。Goならpprof等 | 累積時間と自身の時間を分ける。CPUプロファイルだけではI/O・ロック待ち全体は分からない |
| 何を待っているか | キュー、接続待ち、DBロック、外部通信、必要ならblock/mutex・スレッド等 | 「syscallが多い」だけでDB待ちと断定せず、スタック・回数・別指標で絞る |
| リソースの上限か | CPU、メモリ、I/O、ネットワーク、FD、接続数、ログの容量 | 常時接続、増えた利用者、再試行の増加を含めて見る |
| クライアントが進めない理由 | 成功処理数、状態遷移、要求の順序・待ち、後半の進行、エラー種別 | 特定APIの平均だけで全体を説明しない |

診断を常時有効にする運用は可能。私たちは途中からその方針にした。前後で設定を揃え、slow log閾値、サンプリング時間、同時採取を記録する。大量ログ自体が律速ならサンプリング・対象絞り込みを検討し、変更した比較基準を更新する。

1回のベンチとプロファイルから上位の仮説を少数に絞る。必要な追加測定が具体的なら実行する。「念のため全部再計測」ではなく、次の選択を変えられる測定を行う。

## 4. 候補の選び方と採否

### 仮説カード

AIに次の項目を埋めさせてから変更する。根拠なしの「効きそう」は保留する。

```yaml
id: H-001
current_accepted_commit: 未記入
comparison_run: 未記入
observed_fact: ログのパス、対象、件数、時間、エラー
hypothesis: なぜこの変更が得点処理列を進めるか
expected_effect: 削減する回数・データ量・待ち。総点の推定は推定と明記
change_scope: コード、スキーマ、設定、配備対象
invariants: 順序、一貫性、永続性、初期化など
capacity_check: 負荷増加時に確認する上限
validation: 公式ベンチと必要な追加検証
rollback: 正常状態へ戻すコミット・設定・手順
time_budget: 次の判断までの上限時間
result: 未実施
next_decision: 次に何を測れば採用・不採用を判断できるか
```

優先するのは、得点処理列の現在の律速を、実測の根拠付きで大きく削れる候補。概算には回数×削減単位費用を使えるが、並列性・重なり・負荷の変化があるので、その値をそのまま実時間やスコア上昇率にしない。

### 反復回数を固定しない

- 初期比較はまず1回。明らかな異常・不安定さがあれば原因確認のため追加する。
- 候補はまず1回。FAILならエラーを分類し、候補が狙った指標を変えたかも読む。
- 大きな増加があり、公式検証と指標が整合する候補は、追加計測または再起動後計測で確認する。
- 小差が同じコードの変動幅と重なるなら、改善を断定しない。競技時間に応じて仮採用・保留・差し戻しを選び、その理由を残す。
- 別日・環境・大きな設定変更後は旧コードも短く再確認する。古い最高点を現在の比較値として使わない。
- 正常な採用状態の最終確認は省略しない。

大幅改善の探索中に、微小差の候補へ反復を集中させない。ただしスコアが伸びないだけで、障害修正や次の構造変更に必要な土台まで一律に戻さない。性能改善、機能修正、次の候補の前提を分けて判断する。

### 停止と復元

同じ種類の微調整が続き、直近の測定でその部分が律速でなくなったら別の軸へ移る。L7を一巡しても大きな候補がなく、残り時間に対する期待が低ければ探索を止める。

戻すときはGitのコードだけでなく、DBスキーマ・設定・サービス設定・配備先の余分なファイル・キューも対象にする。初期化後と再起動後に戻ったことを確認する。高得点でも不採用にした候補を、最後に誤って選ばない。

## 5. AIへ渡す状態と記録

会話履歴だけを正本にしない。モデルの切替、コンテキストの圧縮、担当交代、PCやプロセスの再起動に耐えられる状態を残す。

推奨する最小構成は以下。名前はチームの既存運用に合わせてよい。

```text
contest/
  STATE.md                  現在状態。最初に読む
  SPEC.md                   当日仕様と得点処理列、根拠、未確認点
  HYPOTHESES.md             仮説、根拠、結果、採否、再試行条件
  DEPLOY.md                 配備・初期化・復元・再起動の手順
  results/<trial-id>/       成否、スコア、コード、設定、ログ、診断
  graphs/                   全試行、最高値更新、必要なら現在の比較
```

`STATE.md` は現在形で更新する。

```markdown
# 現在状態
更新日時：
終了時刻・残り時間：
公式資料の更新確認：
正常な採用コミット：
配備先・実行中コード・設定：
最後に成功した公式試行：
その比較条件とスコア：
過去最高の有効スコア／その候補の採否：
今回の候補と仮説：
現在の律速を示す測定：
未解決の機能・容量・追試上の問題：
ベンチ／配備の担当と実行状況：
次の一手と判断条件：
復元手順：
```

試行ごとに、時刻、段階、対象コミット／差分、成否、スコア、報告点、ベンチ条件、対象台、重要な設定、プロファイル条件、生ログ、採否を残す。失敗は `score: null`、報告点は別の欄。中止・準備失敗も分類して保存する。

全試行グラフと最高値更新グラフを両方使う。最高値更新だけを見ると、不採用候補、反復のばらつき、失敗、時間の浪費が消える。全試行だけを見ると大きな転換点を見つけにくい。最高値更新は採用済み改善の累積ではなく、観測された最高点の履歴だと明記する。

コードは一つの仮説としてレビューできる単位でコミットする。環境対応、候補、測定、差し戻しを追えるようにする。秘密鍵やログイン状態でコミット・配備が止まらないことを事前に練習する。

## 6. 10月31日までに用意しておくもの

未知の問題の解法を準備するのではなく、当日最初の正常ベンチと改善サイクルに入る時間を短縮する。

| 準備 | 完了の基準 |
|---|---|
| AIに渡す指示と状態管理 | この文書を読ませ、別の会話・モデルがSTATE.mdから現状を復元できる |
| 配備・復元のひな形 | ビルド失敗でベンチに進まず、削除した管理対象ファイルも反映できる |
| 計測・記録・グラフ | 1回の公式計測から結果・条件・生ログを保存し、FAIL込みの2種類のグラフを再生成できる |
| 診断の最小セット | 選ぶ言語・DBに合うCPU／HTTP／DBの診断を負荷中に採取できる |
| 役割と環境の排他 | 共有環境の操作担当が分かり、同時配備・同時ベンチを起こさない |
| 初期化・再起動演習 | 採用状態が復元でき、後から追加したスキーマ・設定・キャッシュも正常に扱える |
| AWS・認証・Gitの動作 | 実際に使うアカウント・権限・端末で必要な操作が通る。規約上必要な環境は公式案内に従う |
| 未知の過去問での練習 | 解法を先に読まず、当日資料・コード・測定だけで1サイクルを完了し、その後に講評と照合する |

残り期間の練習では、微小なスコアを詰めるより、**初期ベンチまでの時間、根拠付きの候補を選ぶまでの時間、誤った候補を戻すまでの時間、状態を引き継ぐ時間**を測る。これらは未知の問題でも役立つ。

## 7. 公式資料と競技中の情報の扱い

2026-10-07に確認した [ISUCON2026レギュレーション](https://isucon.net/archives/59966826.html) は、開発でのAI利用を認め、当日マニュアルを優先する。また、再起動後の動作・書き込まれたデータの取得、競技終了後の追試を要求している。本書のキャッシュ・非同期化の提案は、この要件と当日の詳細を満たす場合に限る。

競技終了前の問題内容・ログ・解答の公開や、チーム外の人物との問題に関するやり取りは禁止される。競技中のコミットや保存はチーム内で行い、公開リポジトリ・公開PRへ自動pushする運用を持ち込まない。AIを開発に使えることと、許可されていない外部サーバーでベンチ対象の処理を実行することは別。最新の公式更新を担当者が確認する。

[ISUCON14の公式講評](https://isucon.net/archives/58869617.html) は、今回の練習途中・振り返りで実際に参照した。これは既に公開済みの過去問の答え合わせに使った資料であり、未知の今回の問題に対する競技中の手順や前提にはしない。代わりに、当日マニュアルと提供コードにある選択肢を早く読み、測定で意味を確かめる。
